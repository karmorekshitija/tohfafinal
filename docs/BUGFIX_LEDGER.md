# Bugfix Ledger

| ID | Name | File(s)+function | Root cause | Exact fix | Regression guard (what must never be reintroduced) |
|---|---|---|---|---|---|
| BUG-1 | Outbox backlog flood | `backend/src/services/ownerNotify.service.js` (`processManualQueue`, `queueTaskEmail`) | The retry query filtered only on `kind`, `owner_email_status`, and attempts without filtering on `status`, allowing historical non-pending rows (`suppressed`, `invalid_number`, `opted_out`, `sent`, `manual_done`, `failed`) to flood owner emails once email credentials become valid. Escalation query also had no age limit. | 1. Added `AND status = 'manual_pending' AND created_at > NOW() - INTERVAL '48 hours'` to retry SELECT in `processManualQueue`.<br>2. Added `AND created_at > NOW() - INTERVAL '48 hours'` to escalation SELECT in `processManualQueue`.<br>3. Added `if (row.status !== 'manual_pending') return;` to `queueTaskEmail`. | Never query or retry owner manual task emails without restricting to `status = 'manual_pending'` and `created_at > NOW() - INTERVAL '48 hours'`; never process row in `queueTaskEmail` when `row.status !== 'manual_pending'`. |
| BUG-2 | Owner email resolved in two different ways | `backend/src/config/whatsapp.js` (`getMode`, `getOwnerEmail`), `backend/src/services/ownerNotify.service.js` (`getRecipientEmail`), `backend/src/services/logistics.service.js` (`createShipment`), `.env.example` | `getMode()` and `logistics.service.js` directly read only `OWNER_NOTIFY_EMAIL`, while `ownerNotify.service.js` `getRecipientEmail()` fell back to `ADMIN_EMAIL`. When only `ADMIN_EMAIL` was set, WhatsApp mode dropped to 'suppressed' despite admin notifications being active, and `.env.example` contained duplicate `OWNER_NOTIFY_EMAIL` declarations. | 1. Added and exported `getOwnerEmail()` in `config/whatsapp.js` returning `(process.env.OWNER_NOTIFY_EMAIL \|\| process.env.ADMIN_EMAIL \|\| '').trim()`.<br>2. Updated `getMode()` in `whatsapp.js` to check `!!getOwnerEmail()`.<br>3. Updated `getRecipientEmail()` in `ownerNotify.service.js` to return `whatsappConfig.getOwnerEmail()`.<br>4. Updated `logistics.service.js` to require `getOwnerEmail` and use it instead of raw `process.env.OWNER_NOTIFY_EMAIL`.<br>5. Removed duplicate `OWNER_NOTIFY_EMAIL=admin@thetohfa.in` line from `.env.example`. | Never read `process.env.OWNER_NOTIFY_EMAIL` directly without the `ADMIN_EMAIL` fallback; always use `getOwnerEmail()` from `config/whatsapp` to guarantee uniform owner email resolution across all services. |
| BUG-3 | isConfigured() accepts placeholder keys | `backend/src/services/email.service.js` (`isEmailConfigured`), `backend/src/services/ownerNotify.service.js` (`isConfigured`) | `ownerNotify.service.js` had a separate, incomplete placeholder check that missed placeholder values like 're_your_api_key_here', causing `ownerNotify.service.js` to treat email as configured while `email.service.js` rejected it. | 1. Added and exported `isEmailConfigured()` in `email.service.js` returning true if `getResendApiKey() !== null`, OR `sanitizeCredentials()` returns both non-empty `user` and non-empty `pass` (no existing functions modified).<br>2. Updated `ownerNotify.isConfigured()` to evaluate `hasEmail && emailService.isEmailConfigured()`, preserving recipient check and startup warning. | Never implement bespoke placeholder checks for email credentials in notification services; always delegate to `emailService.isEmailConfigured()`. |
| BUG-4 | No alert when seller has no WhatsApp number | `backend/src/controllers/webhook.controller.js` (`handleRazorpayWebhook`), `backend/src/controllers/payment.controller.js` (`verifyPayment`) | An `if (seller.whatsapp_number)` guard prevented enqueuing when a seller lacked a WhatsApp number. Consequently, `invalid_number` handling and `queueInvalidNumberAlert` never fired, leaving the store owner unaware of the order. | Removed the `if (seller.whatsapp_number)` check in both controllers, unconditionally invoking `whatsappService.sendSellerOrderNotification(seller.whatsapp_number, ...)` with existing arguments and `.catch` error logging. | Never guard `sendSellerOrderNotification` calls behind client-side null checks on `seller.whatsapp_number`; always allow `whatsappOutboxService.enqueue` to record the attempt and dispatch missing number alerts. |
| BUG-5 | Escalation email loses store name and items | `backend/src/services/ownerNotify.service.js` (`processManualQueue`) | The escalation loop in `processManualQueue` invoked `buildReadyMessage(row)` with no `extra` context, causing generated messages to omit seller item lines and store/buyer name fallbacks. | Reused `fetchSellerItemLines` (for `'seller_new_order'`) and `fetchBuyerName` (for `'buyer_quote'`/`'buyer_proof'`) to construct `extra`, passed `extra` to `buildReadyMessage(row, extra)`, and used `extra.storeName` / `extra.buyerName` as fallbacks for computing `name`. | Never call `buildReadyMessage(row)` in escalation emails without constructing and passing the full `extra` context using `fetchSellerItemLines` and `fetchBuyerName`. |
| BUG-6 | Occasion digest marks rows sent even if email failed | `backend/src/services/ownerNotify.service.js` (`sendOccasionDigest`) | `sendOccasionDigest` ignored the return value of `sendMail`, running `UPDATE ... owner_email_status = 'sent'` even when the email failed or returned error. | Captured `result` from `sendMail` and gated the database UPDATE behind `if (result && result.success === true)`; otherwise logged a warning and left the rows untouched. | Never mark outbox rows `owner_email_status = 'sent'` without validating that `sendMail` returned `result && result.success === true`. |
| BUG-7 | Mark as Sent link can be triggered by email scanners | `backend/src/controllers/admin.controller.js` (`markWhatsAppOutboxDoneByToken`, `confirmWhatsAppOutboxSentByToken`), `backend/src/routes/admin.routes.js` | State mutation occurred directly on GET `/api/admin/whatsapp/outbox/:id/done`, causing email scanner bot prefetching to accidentally mark manual tasks as sent, and the database UPDATE lacked a status guard. | 1. Modified GET `markWhatsAppOutboxDoneByToken` to only verify the HMAC token and render an HTML confirmation page with a "Confirm: I sent it" form.<br>2. Registered new public `POST /whatsapp/outbox/:id/confirm-sent` route before auth middleware handled by `confirmWhatsAppOutboxSentByToken`, which re-verifies the HMAC token and executes `UPDATE whatsapp_outbox SET status = 'manual_done', manual_done_at = NOW() WHERE id = $1 AND status = 'manual_pending'`.<br>3. Preserved "Already Marked as Sent" behavior on both endpoints. | Never execute database state changes on public HTTP GET endpoints triggered from emails; always require user confirmation via POST, and always guard `manual_done` updates with `status = 'manual_pending'`. |
